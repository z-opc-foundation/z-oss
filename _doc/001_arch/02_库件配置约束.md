## 1. 背景：一次事故，两条约束

`z-oss-api` 同时扮演两个角色：

1. **可执行应用**（`z-oss-api-<version>-exec.jar`，独立部署 `oss.zopc.top`，端口 8082）；
2. **库件**（普通 `z-oss-api-<version>.jar`，被别的仓依赖 —— 主壳 `z-opc-main` 就依赖它）。

2026-10-22 实测（只读）：

- **约束 1（classpath 根配置）**：库件把 `application.yml` 放在 **classpath 根** ⇒
  Spring Boot 的默认配置位置 `classpath:/application.yml` 在 classpath 上**只解析到第一个命中**
  ⇒ 库件那份会**顶掉宿主**的 ⇒ 本次主壳的 `spring.datasource.url` 回落成 `localhost`
  ⇒ Druid `max-wait=-1` 无限等待 ⇒ **启动期挂死**（无 `startupProbe` 时被 liveness 每 420 秒判死）。
  详见 lead 仓 `006_部署方案/010_发版收尾清单.md` §3.8。
- **约束 2（同一坐标多种字节）**：同一坐标 `io.github.yuku123:z-oss-api:1.0.4` 有**两种字节** ——
  **中央在架**那份（`f286184b…`，`application.yml` 里**写死**生产 RDS 主机名 / 用户名 / **口令**）
  与**本地 m2 / 线上内嵌**那份（`1a57ef15…`，ENV 形态）。
  而本地 m2 的 `.sha1` 边车**仍写着中央那份的哈希** ⇒ **校验链断裂** ⇒
  任何 sha1 校验都发现不了「它们不是同一份」⇒ **干净环境重建拿到的是带明文口令的那一份**。

## 2. 约束条文（可机械判定）

| # | 约束 | 怎么判 | 门禁在哪 |
|---|---|---|---|
| C1 | **`z-oss-api` 的 jar 内不得有根级 `application.yml` / `application.properties` / `bootstrap.yml`** | `unzip -l <jar>` 看根级条目 | `_doc/003_script/precheck.sh` 第 2 项 |
| C2 | 本仓配置**不得叫** `application*`（改名 `z-oss-standalone.yml`），由启动类用 `spring.config.additional-location` **显式**加载 | 源码 + jar 条目名 | 同上 + `ZOssApplication` |
| C3 | 本地 m2 里本仓坐标的 `.sha1` 边车必须 == **实际字节**的 sha1 | 比对两个 sha1 | `_doc/003_script/precheck.sh` 第 1 项 |
| C4 | 同一坐标在**本地 m2 / 中央在架 / 线上内嵌**的 sha256 必须**一致**（发同一坐标的新版本前） | 三方并排比对 | lead 仓 `006_部署方案/010_发版收尾清单.md` §三·九「制品坐标唯一性门禁」 |

> C1/C2 与 C3/C4 是**两组不同的门禁**，别互相替代：
> C1/C2 管「**配置会不会劫持宿主**」，C3/C4 管「**同一坐标的字节是不是同一份**」。

## 3. 为什么配置改名就够（机制讲清楚）

Spring Boot 的默认配置位置是：

```
optional:classpath:/  optional:classpath:/config/  optional:file:./  optional:file:./config/
```

每个位置按**文件名 `application`**（或 `bootstrap`）去找 `application.yml` / `application-*.yml` 等。

⇒ 文件名**不叫** `application*`（本仓改成 `z-oss-standalone.yml`）⇒ **默认位置一律不命中**
⇒ **谁引用本库都不会被劫持**；
⇒ 本应用自己用 `spring.config.additional-location=classpath:/z-oss-standalone.yml` **显式**加载
⇒ **独立部署行为不变**（实测：改完后 `java -jar z-oss-api-1.0.4-exec.jar` 仍起在 **8082**，
即 `z-oss-standalone.yml` 里的 `server.port` 生效 ⇒ 配置确实被加载到了）。

⚠ 顺带修掉的一个隐患：原启动类把启动异常**吞掉**、只 `println` 然后**以退出码 0 结束**
⇒ 容器侧看到的是「Completed」而不是「CrashLoopBackOff」⇒ **启动失败在编排层看不见**。
现在改成：打印明确失败原因 + **非 0 退出码**（让编排层立刻看见并报警）。

## 4. 怎么跑门禁

```bash
# 构建前（校验本地 m2 校验链）
./_doc/003_script/precheck.sh --m2-only

# 边车与实际字节不符 ⇒ 先修复再构建
./_doc/003_script/precheck.sh --fix-sidecars

# 构建后（校验产物 jar 里没有 classpath 根配置）
./_doc/003_script/precheck.sh --jar-only
```

`package.sh` 已经把这两道接进流程：任一不过 ⇒ **中止构建**（不发布）。

⚠ 重建**必须 `mvn clean`**：`target/classes/` 里会留着上一版的陈旧配置，
不 clean 会被打进新 jar（本轮实测踩过：改名后第一次 `mvn package` 出来的 jar 里
**同时**有 `application.yml`（旧的）和 `z-oss-standalone.yml`（新的））。
